# God View 工程文档索引

## 阅读顺序

1. [产品需求文档](../PRD.md)：定义用户问题、功能范围、交互与验收。
2. [技术架构与技术选型](./TECHNICAL_ARCHITECTURE.md)：定义系统边界、模块、数据流、选型和技术验证。
3. [编码与可维护性规范](./CODING_STANDARDS.md)：定义代码组织和日常实现规则。
4. [代码质量评估与质量门禁](./CODE_QUALITY_STANDARD.md)：定义测试、指标、CI、发布和质量评分。
5. [升级与回滚](./UPGRADE_AND_ROLLBACK.md)：定义协议/存储兼容、扩展升级与安全回退步骤。
6. [架构决策记录](./adr/README.md)：记录重要技术选择及其取舍。
7. [支持矩阵](./SUPPORT_MATRIX.md)：区分已验证环境、CI 目标、Beta 与不支持环境。
8. [Marketplace 发布交接](./PUBLISHING.md)：定义所有者配置、受保护上传与发布后冒烟。

## 文档职责

| 文档     | 回答的问题                    | 不负责                 |
| -------- | ----------------------------- | ---------------------- |
| PRD      | 为什么做、为谁做、做什么      | 具体代码组织和库的细节 |
| 技术架构 | 系统如何拆分、技术如何选择    | 逐行编码风格           |
| 编码规范 | 实现时必须遵守什么            | 产品优先级             |
| 质量规范 | 如何证明达到可合并/可发布标准 | 替代工程判断           |
| 升级回滚 | 如何安全升级、验证和回退      | 自动回滚用户代码       |
| ADR      | 为什么做出某个重大决策        | 覆盖整个系统设计       |

## 维护规则

- 功能范围变化先更新 PRD，再评估技术与质量文档；
- 架构边界、协议真源、存储、权限或核心依赖变化必须写 ADR；
- 编码规则必须能被自动检查，或给出明确的人工评审方法；
- 质量阈值调整必须附基线数据和原因，不得为让失败的 PR 通过而临时降低；
- 文档中的命令、路径、包名和状态必须与仓库保持一致；
- 每个里程碑结束时复查文档中过时的假设和待验证选择。

增量事实链路已实现；公开发布仍以发布证据中的跨平台 CI 和 Marketplace 所有者操作为准。
技术架构中仍标记为“待 Stage 0 验证”的选型不得被描述为永久决策。
