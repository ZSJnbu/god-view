# ADR-0003：Webview 采用 React + Cytoscape，布局用自研确定性算法跑在 Worker 里

> 状态：Accepted
> 日期：2026-08-11
> 决策者：God View 工程团队

## 背景

Webview 要在一块画布上同时表达：项目结构、三档细节层级（分组／模块／文件）、聚合后的
关系、可信度分级、变更进行中的状态，以及用户自己的布局。约束来自几个方向：

- Extension Host 单次同步工作不得超过 100 ms，布局不能阻塞主线程；
- 严格 CSP：禁止内联脚本与远程脚本，Worker 也必须来自扩展自己的资源目录；
- 用户拖动过的节点位置属于用户，Agent 的语义更新不得覆盖；
- 选择与悬停不得触发全图重新布局。

## 决策

1. **React** 负责工具栏、详情栏、状态栏等 DOM 部分，通过 `useSyncExternalStore` 订阅
   `AppStore`，组件本身不持有业务状态。
2. **Cytoscape** 只做渲染映射与交互事件，不作为状态容器。
3. **布局自研**：`layout/layout.ts` 是纯函数，按语义泳道（entry / core / storage / external）
   分列，核心列内部按依赖深度分层，同列按重要度与 label 排序。
4. **布局在 Worker 中执行**：`layout-worker.js` 由扩展通过 `data-worker-src` 注入地址，
   CSP 增加 `worker-src ${webview.cspSource}`。Worker 创建失败时 `LayoutClient` 同步降级，
   功能不消失。
5. **用户坐标优先**：拖拽结果通过 `saveLayout` 命令持久化在扩展侧（按 workspace + 分支），
   布局引擎把这些节点视为固定点，只排布其余节点。

## 候选方案

### 方案 A：React + Cytoscape + 自研布局（已选）

- 优点：布局是纯函数，可单测、可确定性回归；不引入布局库依赖；泳道语义与产品的
  「入口—核心—数据／外部」阅读方向直接对应。
- 缺点：自研布局的美观度不如成熟力导向／层次布局。
- 风险：图规模增长后，泳道内节点过多会显得拥挤。

### 方案 B：Cytoscape + elkjs 层次布局

- 优点：布局质量高，处理复杂层次结构成熟。
- 缺点：elkjs 体积可观（数百 KB），且是 GWT 编译产物，行为难以在单测中断言；
  确定性依赖库的内部实现。
- 风险：Webview bundle 已经接近 800 KB，再加一个大依赖会拖慢首帧。

### 方案 C：纯 SVG 自渲染，不用图库

- 优点：bundle 最小，完全可控。
- 缺点：要自己实现平移缩放、命中测试、拖拽、边路由、视口裁剪。
- 风险：把工程量花在重写图库上，而不是花在产品差异化的可信度呈现上。

## 选择理由

布局是这个产品里少数「必须确定性」的部分——每次刷新都换个样子会直接破坏信任。自研纯函数
布局让确定性变成一条可断言的测试，而不是对第三方库的期望。渲染、交互这类没有差异化价值的
部分则交给 Cytoscape。方案 B 的布局质量优势在当前的泳道式信息结构下并不明显。

## 影响

- 正面：布局可单测（`layout.test.ts` 断言相同输入产生相同坐标）；无额外大依赖。
- 负面：需要自己维护布局质量，节点密集时可能需要迭代算法。
- 无障碍：可信度用颜色 **和** 边框样式双重编码；侧边栏结构树提供不依赖画布的浏览路径；
  `prefers-reduced-motion` 与 VS Code 的减少动态设置关闭镜头补间。
- 性能：布局在 Worker 中执行；选择与悬停只改 Cytoscape 的 class，不重新布局。

## 实施与迁移

已实施于 `apps/webview`。构建产物写入 `apps/vscode-extension/dist/webview`，因为
`localResourceRoots` 只授权了这一个目录。

## 验证标准

- 相同输入两次调用 `computeLayout` 结果逐字段相等；
- 被折叠的节点仍能被搜索命中，并可通过 `resolveVisibleAnchor` 定位到代表节点；
- 聚焦模式明确报告被裁掉的节点数，不假装它们不存在；
- Worker 创建失败时布局仍然产出（`LayoutClient` 降级测试）。

## 回滚方案

若自研布局在真实项目上表现不可接受，`LayoutClient` 的接口允许换成任意实现（包括 elkjs），
调用方无需改动。
