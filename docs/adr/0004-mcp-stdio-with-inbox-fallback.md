# ADR-0004：Agent 传输以 MCP stdio 为主，工作区事件收件箱为兜底

> 状态：Accepted
> 日期：2026-08-11
> 决策者：God View 工程团队

## 背景

God View 需要接收来自不同 Agent 的地图声明。现实情况是：

- 有些 Agent 支持 MCP（Claude Code、Codex），可以直接连接；
- 有些工作流跑在容器、CI 或另一台机器上，无法与扩展建立 stdio 连接；
- 扩展进程是唯一写者，任何传输方式最终都要汇入同一个归约入口；
- 事件来自 Agent，属于不可信输入。

## 决策

**主路径：MCP stdio。** `god-view serve` 以低层 `Server` 暴露八个地图与讲解工具。选择低层 API 而
不是 `McpServer`，是因为工具入参 Schema 由协议真源生成，直接以 JSON Schema 注册即可；
`McpServer` 要求改用 Zod 描述入参，那等于在真源之外再维护一份平行定义（见 ADR-0001）。

**兜底路径：工作区事件收件箱。** `god-view emit` 把事件写进 `.godview/inbox/`：

1. 写临时文件；
2. `fsync` 后原子 `rename` 为正式事件文件；
3. 扩展的 `InboxWatcher` 读取、Ajv 校验、串行交给状态引擎；
4. 处理成功后删除文件；失败的消息进入隔离区。

两条路径汇入同一个 `GraphRepository`，因此幂等、版本检查与拒绝规则完全一致。
`.godview/` 默认不进 Git。

## 候选方案

### 方案 A：MCP stdio + 文件收件箱（已选）

- 优点：覆盖「能连」和「连不上」两类环境；文件路径无需网络端口与鉴权；
  原子 rename 保证读到的永远是完整事件。
- 缺点：两条路径都要测试；收件箱是「至少一次投递」，必须依赖幂等。
- 风险：收件箱目录被用户误提交进 Git。

### 方案 B：只支持 MCP

- 优点：实现最少。
- 缺点：容器、远程和 CI 场景直接不可用。
- 风险：把「Agent 维护地图」限制在少数几个宿主里，产品价值大打折扣。

### 方案 C：本地 HTTP 服务

- 优点：任何语言都能调用。
- 缺点：需要端口管理、鉴权和 CORS；在开发者机器上开监听端口是额外攻击面。
- 风险：鉴权做不好等于把项目结构写入权限暴露给本机任意进程。

## 选择理由

方案 C 的通用性可以由方案 A 的文件路径以更低风险达成：文件系统权限已经由操作系统管好，
不需要再发明一套鉴权。MCP 覆盖交互式场景，收件箱覆盖其余场景，两者共用同一个校验与归约
入口，因此额外成本主要是测试而不是设计复杂度。

## 影响

- 正面：Agent 侧无需网络配置；断线不丢事件（文件留在收件箱里）。
- 负面：收件箱是异步的，Agent 调用 `emit` 后不能立即得到归约结果。
- 安全：不开任何监听端口；所有入站事件经过 Ajv 校验；被拒绝的调用以 `isError` 返回，
  避免 Agent 把校验失败当成成功继续声明。
- 隐私：Gateway 本身不发送任何数据到云端；宿主 Agent 是否上云由其自身政策决定，
  无法确认时按「可能上云」处理并在能力声明中如实标注。

## 实施与迁移

已实施于 `apps/agent-gateway`（CLI 与 MCP server）与
`apps/vscode-extension/src/engine/inbox-watcher.ts`（监听与串行处理）。

## 验证标准

- MCP 契约测试走真实 Client ↔ Server 往返，覆盖工具清单、入参 Schema 与错误映射；
- 未知工具返回错误而不是静默成功；
- 被拒绝的调用 `isError` 为 true 且 `accepted` 为 false；
- 收件箱中的损坏文件进入隔离区且不阻塞后续事件。

## 回滚方案

MCP SDK 出现不兼容变更时，收件箱路径可独立工作，扩展功能不受影响。
