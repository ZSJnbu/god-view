# ADR-0002：事件日志 + 快照的单写者状态引擎，按 workspace 与分支隔离

> 状态：Accepted
> 日期：2026-08-11
> 决策者：God View 工程团队

## 背景

地图由 Agent 增量声明产生，同时用户会拖动布局、确认或否决节点。需要回答几个问题：

- 多个进程（扩展、Gateway CLI、可能的多个 Agent 会话）如何并发写同一张地图；
- 切换 Git 分支后，另一个分支的地图是否应该出现；
- 进程崩溃或写入中断后，如何恢复到一个自洽状态；
- Agent 重试同一个操作时，如何不产生重复节点。

## 决策

1. **单写者**：只有 VS Code 扩展进程写状态。Gateway 把事件写进工作区收件箱目录，
   由扩展读取、校验、归约。禁止多个进程并发追加同一个 JSONL。
2. **事件溯源**：已接受事件顺序追加到 `events.jsonl`，周期性写 `snapshot.json`。
   恢复时优先读快照，再重放其后的事件。
3. **幂等**：事件 ID 由 `sessionId + idempotencyKey` 推导，快照记录 `appliedEventIds`，
   重复事件直接返回当前快照，不推进版本号。
4. **隔离**：存储路径为 `<globalStorage>/<workspaceId>/<branchKey>/`。`workspaceId` 由
   工作区根路径哈希得到，`branchKey` 来自 Git；两者都经过 `toDirectorySegment` 净化后附加
   短哈希，避免路径穿越与碰撞。
5. **原子写**：所有文件写入走「临时文件 → fsync → rename」。读模型 `map.json` 因此始终是
   完整 JSON，Gateway 的 `get_map` 不会读到半个文件。

## 候选方案

### 方案 A：事件日志 + 快照 + 单写者（已选）

- 优点：可回放、可审计、可解释「地图为什么长这样」；崩溃后可恢复；天然支持幂等。
- 缺点：需要维护日志压缩与快照策略；损坏记录需要隔离区。
- 风险：日志无限增长。

### 方案 B：只存最终快照，每次全量覆盖

- 优点：实现最简单。
- 缺点：无法回答「谁在什么时候改了什么」；并发写会整份丢失对方的修改；中断写入即损坏。
- 风险：产品的核心价值之一是「看见项目如何被构建」，丢掉历史等于丢掉这个价值。

### 方案 C：嵌入式数据库（SQLite）

- 优点：并发与事务由数据库解决。
- 缺点：引入原生依赖，跨平台分发成本高；地图规模远达不到需要数据库的量级。
- 风险：VS Code 扩展打包原生模块在多平台上的维护成本。

## 选择理由

地图的规模是「几百个节点」，不是数据库量级；真正的难点是并发、恢复和可解释性。事件溯源
直接解决这三点，且不引入原生依赖。方案 C 的能力在这里是过剩的，代价却是实打实的分发问题。

## 影响

- 正面：任何时刻都能回答地图是怎么变成现在这样的；重试安全；分支切换不会串图。
- 负面：状态引擎的复杂度集中在 `graph-core` 的归约与 `storage` 的恢复路径，这两处必须高覆盖。
- 安全：损坏或非法的事件进入隔离区而不是被丢弃，便于排查而不影响可用性。
- 性能：恢复时间取决于快照之后的事件数，需要定期写快照控制重放量。

## 实施与迁移

已实施于 `packages/graph-core`（纯归约）与 `packages/storage`（持久化与恢复）。
快照记录 Schema 版本，协议升级时通过向前迁移读取旧快照。

## 验证标准

- `graph-core` 行覆盖率 ≥ 95%，`storage` ≥ 90%；
- 重放同一事件序列产生逐字节相同的规范化快照（`canonicalize` + `hashSnapshot`）；
- 损坏的日志行进入隔离区且不阻塞恢复；
- 同一 `idempotencyKey` 重复提交不改变版本号。

## 回滚方案

快照与日志都不可用时，扩展以空图启动并记录 `restoredFrom: none`；用户可让 Agent 重新建图。
不存在需要回滚的破坏性迁移。
